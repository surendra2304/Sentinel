## 2. Architecture and core task flow — Phases 2, 5, and 12

### Normal flow

1. **Ingress. [FACT]** `POST /api/v1/tasks` converts request targets and calls `TaskLifecycleManager.create_and_submit_task`; the endpoint returns a task ID and current status. [sentinel/apps/api/main.py:310–338](sentinel/apps/api/main.py#L310-L338)
2. **Scope/admission. [FACT]** Lifecycle requires a caller scope with owner, written authorization reference, time window, allowed methods, maximum impact, positive rate limit, and target binding. It validates the scope and each requested target before storage, records task creation, emits events, and schedules an in-process asyncio job. [sentinel/core/orchestrator/lifecycle.py:48–183](sentinel/core/orchestrator/lifecycle.py#L48-L183)
3. **Planning. [FACT]** The default `HeuristicPlanner` generates staged recon/discovery work. Passive mode terminates after passive baseline; other modes continue to HTTP observation/technology fingerprint and a service scan. The planner’s phases are deterministic heuristics; specialist agent names in the default plan are limited. [sentinel/core/orchestrator/orchestrator.py:73–93](sentinel/core/orchestrator/orchestrator.py#L73-L93) · [sentinel/core/planner/heuristic.py:55–245](sentinel/core/planner/heuristic.py#L55-L245)
4. **Policy and adapter execution. [FACT]** Each action is checked by `PolicyEngine`, then dispatched to the registered adapter. The executor uses a per-process semaphore (default 25), handles retry/abort paths, and records output as evidence. [sentinel/core/orchestrator/executor.py:95–123,136–218](sentinel/core/orchestrator/executor.py#L95-L123) · [sentinel/core/policy/engine.py:150–340](sentinel/core/policy/engine.py#L150-L340)
5. **Evidence/findings/report. [FACT]** Evidence bytes are SHA-256 hashed and stored with metadata; agents’ observations are checked for matching task IDs and references to supplied evidence before ingestion. Lifecycle later generates a technical report and persists the terminal task result. [sentinel/storage/evidence/store.py:44–125](sentinel/storage/evidence/store.py#L44-L125) · [sentinel/core/orchestrator/orchestrator.py:390–425](sentinel/core/orchestrator/orchestrator.py#L390-L425) · [sentinel/core/orchestrator/lifecycle.py:218–259](sentinel/core/orchestrator/lifecycle.py#L218-L259)

## 12. Priorities and first-change guidance

1. **First next change: verify authorization and identity.** Bind the declared owner and authorization reference to a trusted identity/ticket/asset-ownership source. Until then, a complete scope proves only that a caller supplied a structurally valid claim.
2. **Do not scale the current worker model yet.** Add shared task leases/claims, idempotent state transitions, distributed cancellation/kill-switch propagation, tenant context, and truthful database/object-store health before using multi-replica deployment.
3. **Anchor audit history outside the ledger.** Add a trusted last-sequence/hash checkpoint, rotation/retention, efficient append semantics and multi-process coordination. The v2 changes address metadata edits, not chain deletion or valid-prefix rollback.
4. **Finish network/resource boundaries.** The scanner now caps port lists and Python-fallback socket concurrency; characterize Nmap and multi-task loads next. Use explicit TLS trust/CA controls rather than unconditional `verify=False`, bound subprocess memory/output/time, and apply data-sharing consent to all research/inference routes.
5. **Complete end-user acceptance.** Add browser-to-running-API task creation/progress/report/cancel tests and exercise failures/cancellation during a real adapter action (the current in-flight cancellation test blocks a local worker function). Assess finding quality only against an explicitly authorized controlled corpus.
6. **Validate deployment dependencies.** Run Docker/Compose, PostgreSQL, object store, readiness, migrations, restart recovery, backup/restore and TLS proxy checks before making production claims.

## 14. Comprehension quiz and answer key

1. What planner drives ordinary tasks by default, and is an LLM planner active?
2. What must a normal task’s scope declare? Does a written reference prove authorization exists?
3. How did the FRIDAY scope behavior change, and what trust issue remains?
4. What changed in the dashboard task flow, and what has not been tested end-to-end?
5. Which path gates normal adapter execution: `ActionRouter` or `ExecutionEngine`/`PolicyEngine`?
6. What does the new local API-to-report test establish, and what does it not establish?
7. Which audit fields are authenticated in v2, and what does an external head anchor add?
8. What does evidence ZIP v2 verification check? What is weaker in legacy v1?
9. Why is the three-replica Kubernetes declaration not evidence of safe horizontal task execution?
10. What do 352 passing tests establish here—and what do they not?

### Answer key

1. `HeuristicPlanner` is the default; the optional LLM planner/provider is not wired into ordinary task execution.
2. Owner, written authorization reference, target allowlist, allowed methods, active bounded time window, maximum impact, and positive rate limit. Sentinel validates declaration shape/boundaries but does not verify a trusted ticket or the truth of the owner’s claim.
3. FRIDAY now rejects absent/partial scope and no longer synthesizes authorization; default `assessment` stays assessment. Caller-supplied owner/reference still are not verified against an authorization authority.
4. The form now submits explicit scope and reports API validation detail, with third-party enrichment off by default. Component tests mock the API; a browser connected to a running service remains untested.
5. The normal path is `ExecutionEngine` → `PolicyEngine` → adapter registry. `ActionRouter` is a separate abstraction not used by the ordinary task pipeline.
6. One scoped API task reaches a loopback fixture, completes all recorded actions, produces a missing-header finding linked to same-task evidence, and includes it in a retrievable report. Other API tests reject expired/future/out-of-scope scope and cancel a controlled in-flight worker. These checks do not prove finding accuracy beyond the fixture, browser usability, deployment durability, or throughput.
7. New v2 records authenticate sequence, timestamp, tenant/action context and other entry fields; sequence continuity is checked. An external trusted head checkpoint is needed to detect deletion or rollback to a valid prefix. Legacy v1 records have weaker metadata coverage.
8. V2 recomputes a canonical manifest hash, verifies the HMAC signature, checks artifact paths/count/size/SHA-256. V1 is checksum-only and has no authenticated manifest.
9. The manifest lacks a safe shared worker/lease/service/storage setup; task jobs and important state are process-local. Multiple replicas can diverge or duplicate recovery work.
10. It proves the automated assertions passed under the local test profile. It does not prove real-world scan accuracy, user/browser acceptance, production readiness, multi-replica correctness, or security of untested paths.
